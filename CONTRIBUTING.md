# Contributing to Vib Docs Engine (`vib-docs-engine`)

Thank you for your interest in contributing to **Vib Docs Engine**, the configuration-driven static multi-product documentation engine maintained by **[Vib Tools](https://vib.tools/)**.

This guide explains how to set up your local environment, keep product documentation separated from engine code, follow our documentation-first change process, and verify your changes before opening a pull request.

---

## 1. Core Architectural Boundaries

Before making changes, keep these non-negotiable rules in mind:

1. **Configuration-Driven Only:** Portal identity (`config/site.config.json`), product registries (`config/projects.json`), and per-repository settings (`.vibtools/docs.config.json`) control all products, categories, logos, and portal routing (`users`, `developer`, `all`). Never hardcode product slugs, titles, or categories inside application UI components.
2. **Product Docs Stay in Product Repositories:** Do not author documentation for external products inside this repository. Product documentation lives in `https://github.com/vibtoolshq/<repo>` (open-source projects) or `https://github.com/vibdocs/<repo>` (public docs-only repositories).
3. **Never Hand-Edit Generated Paths:**
   - `src/content/docs/` (populated by `npm run sync`)
   - `src/generated/manifest.json` (generated by `npm run sync`)
   - `public/logos/` (except tracked brand assets; product logos are copied during `npm run sync`)
   - `dist/` (static build output)
4. **Zero Credentials in Source or Config:** Never commit tokens, private keys, or credential-bearing URLs into `config/projects.json`, presets, notes, or tests. Always use environment variable references such as `"$GIT_TOKEN"`.

---

## 2. Documentation-First Workflow (`AGENTS.md`)

Every code, configuration, or documentation change in this repository follows `AGENTS.md`:

1. **Inspect First:** Read the relevant source files, `project/` specifications, and `docs/` guides.
2. **Plan in `notes/`:** Create or update a dated plan in `notes/` (and register new files in `notes/MANIFEST.md`) describing the goal, inspected files, focused implementation steps, and verification check before editing implementation files.
3. **Implement Narrowly:** Keep changes focused on the requested bug fix or feature. Avoid unrelated refactoring or dependency upgrades.
4. **Update Durable Documentation:**
   - Update `project/04-codebase-reference.md` (and any affected `project/01`–`03` spec) when modules, functions, or behavior change.
   - Update `docs/` when operator, `.vibtools/`, or reader-facing behavior changes.
   - Append a dated entry to `project/CHANGELOG.md`.
   - Keep `README.md` and `MANIFEST.md` files accurate in tracked, non-routable authored directories. (Never add local Markdown files inside `src/pages/` or `functions/` because route scanners treat files there as routes.)

## 3. Local Development Setup

### Prerequisites

- **Node.js:** `>= 22.23.4` (pinned to **`22.23.5`** in `.node-version` and `.nvmrc`)
- **npm:** Uses `package-lock.json` (do not commit conflicting `bun.lock` or `yarn.lock` files)
- **Git:** Git `2.25+` with `sparse-checkout` support

### Setup Commands

```sh
# 1. Install exact locked dependencies
npm ci

# 2. Synchronize configured product docs and build manifest.json
npm run sync

# 3. Start local Astro dev server on http://localhost:3000
npm run dev
```

---

## 4. Mandatory Verification Before Submitting a Pull Request

Every pull request must pass all four checks with zero errors:

```sh
# 1. Run unit tests (node:test via tsx — 17+ unit tests across search, seo, vibtoolsConfig)
npm test

# 2. Run Astro/application TypeScript check
npm run lint

# 3. Run Cloudflare Pages Functions isolated TypeScript check
npx tsc -p functions/tsconfig.json --noEmit

# 4. Run full production build, Pagefind indexing, and post-build verifier
npm run verify
```

What `npm run verify` checks automatically:
- `.vibtools/docs.config.json` schema, path containment, and single-file conflict rules
- `.node-version` and `.nvmrc` parity (`22.23.5`) and `package-lock.json` registry integrity
- Absence of leaked governance files (`dist/MANIFEST.md`, `dist/README.md`) or workspace artifacts
- Presence of all required static assets (`/llms.txt`, `/llms-full.txt`, `/schemas/vibtools-docs.schema.json`, `/robots.txt`, `/sitemap-index.xml`, favicons, OG image, brand logo, `_headers`, `_redirects`, `_routes.json`)
- Every manifest route, per-product `llms.txt`, and per-page `.md` raw Markdown export
- Valid `JSON.parse()` on every `<script type="application/ld+json">` tag and `noindex` on `dist/404.html`
- Zero broken internal `href` links or missing `img[src]` assets across all built HTML files

## 5. Adding or Testing a Developer Repository

- To register a `.vibtools/`-enabled developer repository (`"docsType": "developer"` or `"dev"`):
  ```sh
  npm run add-project -- --url https://github.com/vibtoolshq/SocketCore.git
  ```
- To test standalone developer portal export locally:
  ```sh
  npm run export-portal -- --portal dev --out /tmp/test-dev-portal
  ```

## 6. Submitting Issues and Pull Requests

- **Bug Reports:** Use the **[Bug report](.github/ISSUE_TEMPLATE/bug-report.yml)** form and include reproducible steps, expected vs. actual behavior, and environment details.
- **Feature Requests:** Use the **[Feature request](.github/ISSUE_TEMPLATE/feature-request.yml)** form and confirm that the proposal preserves the static, configuration-driven architecture.
- **Pull Requests:** Follow **[`.github/PULL_REQUEST_TEMPLATE.md`](.github/PULL_REQUEST_TEMPLATE.md)** and check off all verification and documentation items.
- **Security Issues:** Do **not** open a public issue for security vulnerabilities. Follow **[`SECURITY.md`](SECURITY.md)** and report privately to **[support@vibtools.io](mailto:support@vibtools.io)**.
